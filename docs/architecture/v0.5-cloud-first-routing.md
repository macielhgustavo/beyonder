# v0.5 Cloud-First Quality-Gated Routing

Status: v0.5 architecture, zero-money. Paid escalation is represented but disabled.

## BEFORE_ROUTING_POLICY

The adaptive router already combined provider inventory, quota scarcity, BIB capability priors, historical outcomes, latency, failure risk and Economic Memory signals. However, execution still inherited two local-first biases:

1. remote and local models lived in a mostly flat utility-ranked pool;
2. `runCandidates` reserved room for a local candidate inside the normal candidate limit, so a local model could displace another qualified cloud attempt;
3. survival mode explicitly budgeted one remote attempt followed by one local fallback;
4. Ollama had zero shadow cost and no policy-level emergency classification;
5. model availability and workload compatibility were not separated from mission-level capability acceptability;
6. when no acceptable model existed, downstream code could collapse the condition into a generic no-candidates/failure path or a weak deterministic planning fallback.

This meant `cloud failed -> local exists -> try local` could occur without proving that the local model was good enough for the mission.

## AFTER_ROUTING_POLICY

Routing now has two independent gates:

1. **availability/compatibility**: provider health, workload compatibility, context, structured-output support, cooldowns, zero-money policy;
2. **acceptability**: mission quality floor and multidimensional capability fit.

Only candidates passing both gates enter the executable queue.

Execution order is:

1. `STRONG_FREE_CLOUD`
2. `OTHER_FREE_CLOUD`
3. `PAID_DISABLED` (architecture placeholder; not executable in v0.5)
4. `LOCAL_EMERGENCY`

Cloud candidates are ordered by mission-adjusted expected quality rather than first-free discovery order. Qualified local candidates remain visible but are always after qualified cloud candidates. The executor has separate remote and local budgets, so local no longer consumes or reserves a remote slot.

## Quality floor

A mission quality floor is derived from the existing `IntelligenceTask` and `GoalContract`, not from model size. The floor has an overall threshold and mission-specific dimensions:

- reasoning
- planning
- coding
- research
- synthesis
- tool use
- structured output
- verification
- freshness/evidence

Signals used to estimate a candidate's ability to clear the floor include:

- BIB capability evidence;
- real historical success and evaluation scores;
- declared model capabilities;
- workload fit;
- provider/model reliability;
- operational health/cooldowns;
- latency;
- context window;
- tool-calling support;
- structured-output support;
- quota scarcity and Economic Memory shadow cost.

Current/realtime multi-source research and evidence-heavy comparison objectives are promoted to a HIGH floor. Complexity increases the numerical floor. A model that is online but does not clear the floor is recorded as rejected and is not executable.

## Local emergency compute

Ollama models are catalogued truthfully as available local models, but routing policy classifies them as `LOCAL_EMERGENCY`.

Local is eligible only when all of the following are true:

- the model is workload-compatible;
- it clears the mission's overall and dimensional quality floor;
- it is operationally available;
- it fits cumulative time/resource budgets;
- no qualified cloud candidate succeeds first.

Local is prohibited when any required capability dimension is below the floor. A local model is not promoted because it has zero monetary cost, unlimited local quota, or low API scarcity.

Local compute now carries a non-zero shadow-cost floor to represent CPU/GPU opportunity cost and latency/resource use.

## Fallback available != fallback acceptable

Availability answers: "Can this model run?"

Acceptability answers: "Should this model be trusted for this mission?"

The second question is authoritative. An available Ollama model below the mission floor is kept in audit evidence as rejected but is never attempted. If no acceptable model remains, the route becomes `NEEDS_CAPABILITY`.

## Degraded mode

If no cloud is usable but a local emergency model clears the floor, routing returns `CAPACITY_REDUCED` and runs the local airbag.

If no model clears the floor, routing returns `NEEDS_CAPABILITY`. Downstream inference and planning preserve that state; they do not substitute a weak deterministic planner. `ObjectiveVerifier` maps capability shortage to a blocked objective, never to success and never to a generic completed state.

## Budgets and retries

Remote and local budgets are independent. In survival mode, up to two qualified remote attempts may be used before one local emergency attempt. Existing cumulative time, monetary-cost and shadow-cost budgets remain authoritative.

A local attempt is permitted only after remote failures that are plausibly recoverable by changing compute (provider unavailable, rate limit, timeout, network/model availability/auth-style provider failures). Invalid output from a remote model does not automatically justify dropping to weaker local compute.

## Paid compute readiness

The tier model includes `PAID_DISABLED` so future policy can evolve toward:

`FREE CLOUD -> CHEAP PAID -> PREMIUM PAID -> LOCAL EMERGENCY`

v0.5 does not enable paid escalation, does not spend money, and continues excluding billing-risk/unknown-cost inventory from normal candidate generation. Future paid activation requires an explicit economic policy and approval boundary.

## Observability

Routing emits auditable events for:

- `router.quality_floor_resolved`
- `router.candidates_generated`
- `capability.resolved`
- `quota.updated`
- `shadow_cost.calculated`
- `router.candidate_scored`
- `router.candidate_rejected`
- `router.capacity_reduced`
- `router.needs_capability`
- `router.selected`

Candidate-scored/selected events include tier, eligibility, rejection reasons, routing score, capability fit, predicted quality, BIB/outcome evidence, historical success, reliability, monetary cost, shadow cost, latency penalty, failure risk and effective resource cost.

## Product invariants preserved

This policy does not weaken or bypass:

- GoalContract semantics;
- ObjectiveVerifier / zero false success;
- browser evidence boundaries;
- approval boundaries;
- execution checkpoints and leases;
- side-effect reconciliation;
- SQLite durability;
- mission/work separation;
- settlement evidence;
- Control Center truthfulness.

The key invariant is now: **no mission may be marked successful merely because some compute was available. The compute used must first be acceptable for the mission.**
